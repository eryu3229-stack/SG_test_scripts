## 修复扫描超时问题

运行时发现窄 RBW + 多次 MAXH 扫描导致 `wait_for_sweep` 超时，进而读取 trace 失败。

- `instruments/spectrum_analyzer.py`
  - `wait_for_sweep` 原超时只按单次扫描时间 × 2.5 计算，未乘 `sweep_count`。
  - 改为：总超时 = `sweep_count × sweep_time × 3`，兜底也从 5 分钟改为按 sweep_count 递增。
  - 已通过 `python -m py_compile` 语法检查。

如果仍超时，可降低 `spurious_config.py` 中的 `sweep_count`，或改用更宽 RBW。

## 修复 wait_for_sweep 超时后程序卡住

用户报 `VI_ERROR_TMO: Timeout expired before operation completed.`，之后程序卡住无下文。

根因：
- `wait_for_sweep` 超时返回 False 后，调用方未检查返回值，继续调用 `get_trace()` / `peak_search()`，仪器状态异常导致二次超时/挂死。
- `INIT:IMM` 与 `*OPC?` 分开发送，在部分 R&S 频谱仪上同步不可靠。

修改：
- `instruments/spectrum_analyzer.py`
  - `wait_for_sweep` 改用 `INIT:IMM;*OPC?` 合并查询，确保 *OPC? 在扫描完成后才返回。
  - 超时后调用 `_cleanup_after_timeout()` 发送 `ABOR;INIT:CONT ON;*CLS` 复位仪器状态。
  - 使用 `finally` 恢复原始 VISA timeout。
- `procedures/spurious_procedure.py`
  - 6 处 `wait_for_sweep` 调用均检查返回值，失败时跳过当前 segment/候选/谐波/载波。

已通过 `python -m py_compile` 语法检查。

## 加固 N9030B trace 读取

用户反馈频谱仪扫描 5 次后程序卡住，怀疑卡在读取迹线阶段。

根因：
- N9030B 可能返回二进制块数据，原 `get_trace` 直接按 ASCII 逗号拆分可能解析失败/超时。
- trace 数据量大时默认 read timeout 不足。

修改：
- `instruments/spectrum_analyzer.py`
  - `get_trace` 先发送 `FORM:DATA ASC` 强制 ASCII 格式。
  - 读取超时临时放大到 30 秒。
  - 兼容二进制块头解析（以 `#` 开头时按 header 长度跳过）。
  - 增加原始数据长度与前 80 字符的调试打印。
  - 使用 `finally` 恢复原始 timeout。

已通过 `python -m py_compile` 语法检查。

## wait_for_sweep 改用状态寄存器轮询

用户再次报 `VI_ERROR_TMO`，确认 N9030B 上 `*OPC?` 不可靠。

修改：
- `instruments/spectrum_analyzer.py`
  - `wait_for_sweep` 不再使用 `*OPC?`，改为轮询 `STAT:OPER:COND?` 的 bit 4（value=16）。
  - bit 4 为 1 表示正在扫描，变为 0 表示单次扫描完成。
  - 每次 `INIT:IMM` 后单独轮询，适配 sweep_count 次扫描。
  - 超时或状态查询失败时调用 `_cleanup_after_timeout()` 复位。

已通过 `python -m py_compile` 语法检查。

## wait_for_sweep 改用 *OPC + *STB? 轮询

用户报"第 1/5 次扫描状态寄存器轮询超时"，说明 `STAT:OPER:COND?` bit 4 在 N9030B 上不反映扫描完成。

- `instruments/spectrum_analyzer.py`
  - `wait_for_sweep` 改用 `*CLS;INIT:IMM;*OPC` 触发，轮询 `*STB?` 的 bit 5（ESB summary）。
  - 每次扫描完成后 `*CLS` 清掉 ESR 中的 operation complete 位。
  - 保留调试打印，显示每次 `*STB?` 返回值。

已通过 `python -m py_compile` 语法检查。

## 修复屏幕上 AVG|HOLD 100 导致每次 INIT 等 100 次扫描

用户指出仪器屏幕显示 "AVG|HOLD 100"，这是超时根因：每次 `INIT:IMM` 都要等仪器完成 100 次扫描，
`sweep_count=5` 时实际要等 500 次。

修改：
- `instruments/spectrum_analyzer.py`
  - `set_trace_mode` 中设置 `TRAC:AVER:COUN 1`、`AVER:COUN 1`、`SWE:COUN 1`，重置仪器上的平均/扫描计数。
  - `wait_for_sweep` 使用 `SWE:COUN {sweep_count}` 一次性设置扫描次数，再 `INIT:IMM;*OPC` + `*STB?` 轮询等待完成。
  - 这样 MAXH 模式仍能累积 sweep_count 次扫描结果，但每次 INIT 不再受屏幕上残留计数影响。

已通过 `python -m py_compile` 语法检查。

## 移除不支持的 SWE:COUN 和 AVER:COUN，改用连续扫描 + 固定等待

用户提供的 N9030B 手册（Analog Demod Mode Programmer's Reference）中确认：
- 不存在 `SWE:COUN` 命令。
- `AVER:COUN` 只存在于 AM/FM/PM 解调测量子系统（[:SENSe]:AM:AVERage:COUNt 等），不是 trace 平均/扫描计数。
- 正确的初始化命令是 `INITiate:CONTinuous` 和 `INITiate[:IMMediate]`。

由于无法可靠清除屏幕上的 "AVG|HOLD 100" 设置，且 *OPC/*ESR 同步不工作，决定：
- 放弃仪器端同步，改用连续扫描 + 固定延时。

修改：
- `instruments/spectrum_analyzer.py`
  - `set_trace_mode` 删除 `AVER:COUN 1` 和 `SWE:COUN 1`。
  - `wait_for_sweep` 改为 `INIT:CONT ON`，等待 `sweep_count × sweep_time × 1.2 + 2` 秒，再 `INIT:CONT OFF`。
  - 额外等待一次扫描时间确保当前扫描完成后再读取 trace。

已通过 `python -m py_compile` 语法检查。
